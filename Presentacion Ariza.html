01 · El desafío

Un servidor tradicional corre 24/7 haya o no tráfico. Serverless propone lo opuesto: el código se ejecuta —y se cobra— sólo cuando hay algo que hacer.

Servidor tradicional

  • Corre 24/7, haya o no tráfico
  • Se paga por tiempo encendido, no por uso real
  • Escalado manual o con reglas complejas
  • Hay que parchear el sistema operativo

Serverless / FaaS

  • Se levanta sólo cuando llega un evento
  • Se factura por milisegundos y por petición
  • Escala automáticamente de 0 a miles de instancias
  • El proveedor administra el servidor por completo

04 · El problema del Cold Start

Arranque en frío: la demora en responder cuando la función no se invocó en un tiempo y su contenedor se apagó.

¿Qué pasa? Se aprovisiona un contenedor nuevo, se inicializa el runtime, se carga el código y recién ahí se ejecuta el handler.

¿De qué depende? Del lenguaje (Java/.NET más lento que Node/Python), del tamaño del paquete, de la memoria asignada y de si está en una VPC.

04 · Cómo se soluciona el Cold Start

Seis estrategias que se pueden combinar según el proveedor y el caso de uso.

Concurrencia aprovisionadaMantener instancias ya "calientes" listas (Provisioned Concurrency, min instances, plan Premium).
Ping de mantenimientoInvocar la función cada pocos minutos con un cron para que no se apague.
Reducir el paqueteSacar dependencias no usadas y minimizar el tamaño del deploy.
Runtime livianoPreferir Node.js, Python o Go antes que Java o .NET.
Más memoriaEn AWS, más memoria implica más CPU y arranque más rápido.
Reusar conexionesInicializar clientes/SDKs fuera del handler para reaprovecharlos entre invocaciones warm.

06 · Guía rápida para la defensa (1/2)

Respuestas cortas, para decir de memoria en 15-20 segundos.

¿Qué es serverless?
El proveedor administra toda la infraestructura y el código se ejecuta —y se factura— sólo ante eventos concretos.
¿No hay servidor entonces?
Sigue habiendo servidores; lo que desaparece es la necesidad de administrarlos.
¿Cómo se cobra?
Por cantidad de peticiones más el tiempo de cómputo real en GB-segundo.
¿Qué es el cold start?
La demora en responder la primera invocación luego de estar inactiva, por tener que levantar el contenedor de nuevo.

06 · Guía rápida para la defensa (2/2)

El resto de las preguntas más probables.

¿Cómo se mitiga el cold start?
Concurrencia aprovisionada, pings periódicos, paquetes chicos y runtimes livianos.
¿Diferencia clave entre los tres?
Mismo concepto, distinto ecosistema: AWS, Google Cloud/Firebase o Microsoft/.NET.
¿Qué dispara el caso de imágenes?
La creación de un objeto nuevo en el storage, que notifica automáticamente a la función.
¿Ventaja frente a un server tradicional?
Se paga sólo el tiempo real de ejecución y el escalado es automático.
