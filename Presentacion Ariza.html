01

El desafío

En el modelo tradicional, un servidor (físico o virtual) permanece encendido las 24 horas, reciba o no tráfico. Serverless propone lo opuesto: el código sólo se ejecuta —y se cobra— cuando realmente hay algo que hacer.

Servidor tradicional

  • Corre 24/7, haya o no tráfico
  • Se paga por tiempo encendido, no por uso real
  • Escalado manual o con reglas complejas
  • Alguien tiene que parchear el sistema operativo

Serverless / FaaS

  • El proveedor levanta el código sólo cuando llega un evento
  • Se factura por milisegundos de ejecución y por petición
  • Escala automáticamente de 0 a miles de instancias
  • El proveedor administra el servidor por completo

04

El problema del Cold Start

¿Qué es? Cuando una función no se invocó en un tiempo, el proveedor apaga el contenedor que la ejecutaba. La próxima petición que llega tiene que esperar a que se levante todo de nuevo antes de correr el código: eso es el arranque en frío.

¿Qué pasa durante ese arranque? Se aprovisiona un contenedor nuevo, se inicializa el runtime (Node, Python, JVM, etc.), se descarga y carga el paquete de código y recién ahí se ejecuta el handler.

¿De qué depende su duración? Del lenguaje (Java/.NET arrancan más lento que Node/Python), del tamaño del paquete desplegado, de la memoria asignada y de si la función está dentro de una VPC.

Cómo se soluciona

Concurrencia aprovisionadaMantener instancias ya "calientes" listas para responder (Provisioned Concurrency en AWS, funciones mínimas en GCF, plan Premium en Azure).
Ping de mantenimientoInvocar la función cada pocos minutos con un evento programado (cron) para que no se apague el contenedor.
Reducir el paqueteSacar dependencias que no se usan y minimizar el tamaño del deploy para que cargue más rápido.
Runtime livianoPreferir Node.js, Python o Go antes que Java o .NET si el arranque frío es crítico.
Más memoria asignadaEn AWS, más memoria implica también más CPU, lo que acelera la inicialización.
Reusar conexionesInicializar clientes de base de datos o SDKs fuera del handler para reaprovecharlos entre invocaciones warm.

06

Guía rápida para la defensa oral

Tocá cada pregunta para ver la respuesta corta. Pensadas para responder de memoria en 15-20 segundos cada una.

¿Qué es serverless, en una frase?+
Un modelo donde el proveedor cloud administra toda la infraestructura y el código sólo se ejecuta —y se factura— ante eventos concretos.
¿Serverless significa que no hay servidor?+
No, sigue habiendo servidores. Lo que desaparece es la necesidad de administrarlos: el proveedor se encarga de aprovisionarlos, escalarlos y mantenerlos.
¿Cómo se cobra una función?+
Por cantidad de peticiones/invocaciones más el tiempo de cómputo real medido en GB-segundo (memoria asignada por duración de la ejecución).
¿Qué es el cold start?+
La demora en responder la primera invocación después de un período inactivo, porque hay que levantar un contenedor y el runtime desde cero.
¿Cómo se mitiga el cold start?+
Con concurrencia aprovisionada / instancias mínimas, pings periódicos, paquetes de deploy más chicos y runtimes livianos.
¿Cuál es la diferencia clave entre los tres proveedores?+
El mismo concepto con distinto ecosistema: Lambda se integra mejor con AWS, GCF con Firebase/Google Cloud, y Azure Functions con entornos .NET / Microsoft.
¿Qué evento dispara el caso práctico de imágenes?+
La creación de un objeto nuevo en el storage (S3, Cloud Storage o Blob Storage), que notifica automáticamente a la función.
¿Cuál es la ventaja principal frente a un servidor tradicional?+
Se paga sólo por el tiempo real de ejecución y el escalado es automático, sin mantener nada encendido de forma permanente.
